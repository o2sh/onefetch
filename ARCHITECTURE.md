# Architecture

Onefetch reads a Git repository, collects information about it, and prints that
information next to the logo of the repository's main language (or as JSON/YAML).

```
command line ──► cli ──► options ──┬── InfoOptions ───► info::build_info ──► Info ──┐
                                   │                     (git, language)           ▼
                                   └── RenderOptions ─────────────────────► render::Printer ──► stdout
                                                                            (layout, ascii, image)
```

## Modules

| Module      | Role                                                                                       |
| ----------- | ------------------------------------------------------------------------------------------ |
| `cli`       | The clap definition of the command line.                                                   |
| `options`   | Turns `Cli` into `info::InfoOptions` (what to collect) and `render::RenderOptions` (how to print it). The only module that reads `Cli`, apart from `main`. |
| `info`      | Collects data. `build_info` returns an `Info`: a title and a list of `Field`s.             |
| `git`       | Repository queries shared by the fields, notably the single commit-graph traversal.        |
| `language`  | The `Language` enum, generated by `build.rs` from `languages.yaml` and `src/language/language.tera`. |
| `render`    | Prints an `Info`: terminal layout, colors, ascii art, images, and JSON/YAML output.        |

Dependencies only go one way:

- `info` and `git` must not depend on `cli`, `options`, `render`, clap, or colors.
- `render` must not depend on `cli` or `options`. (`cli` uses a few `render`
  types as flag values, such as `SerializationFormat` and `ImageProtocol`.)
- `language` is shared by `info` and `render`: its enum carries both data
  (tokei mapping, language type) and display information (logo, colors, chip).

Everything is one crate, so the compiler doesn't enforce these rules; keep
them in mind when reviewing imports in these modules.

## Collecting data (`info`)

`build_info` opens the repository and computes the expensive inputs once, in
parallel: lines of code per language (tokei, in a thread) and commit statistics
(one commit-graph traversal). They are stored in a `RepoContext` (`info/context.rs`).

Each field is a plain data struct in `info/fields/<name>.rs` with a constructor.
`info/fields/mod.rs` defines:

- `enum Field`, one variant per field, in display order. Its `Serialize` impl is
  the JSON/YAML format of `-o` (`{"HeadInfo": {...}}`), so treat it as a public format.
- `FieldKind`, generated from `Field` by strum, which is what `--disabled-fields` takes.
- `Field::collect`, which builds the field of a given kind from the `RepoContext`.

## Displaying data (`render`)

`render/fields/<name>.rs` implements `FieldView` (`key` and `value` lines) for
the field of the same name in `info/fields/`, using `FormatOptions`
(`render/format.rs`) for numbers, dates and language chips. `render::layout`
turns an `Info` into styled lines, `render::ansi` turns those into terminal
escape codes, and `render::Printer` places them next to the ascii art
(`render::ascii`) or an image (`render::image`), or prints JSON/YAML instead.

## Adding an info field

1. Add `info/fields/<name>.rs` with the data struct (`#[derive(Serialize)]`) and
   its constructor, and declare it in `info/fields/mod.rs`.
2. Add a variant to `Field` in `info/fields/mod.rs`. The compiler then points at
   the `match` arms to fill in: `Field::collect`, `Serialize for Field`, and
   `render::fields::view`.
3. Add `render/fields/<name>.rs` implementing `FieldView` for the struct, and
   declare it in `render/fields/mod.rs`.

The new kind is accepted by `--disabled-fields` automatically.
