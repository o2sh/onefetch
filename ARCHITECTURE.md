# Architecture

Onefetch reads a Git repository, collects information about it, and prints that
information next to the logo of the repository's main language (or as JSON/YAML).

```
command line ──► cli ──► options ──┬── InfoOptions ───► data::build_info ──► Info ──┐
                                   │                     (language)                ▼
                                   └── RenderOptions ─────────────────────► render::Printer ──► stdout
                                                                            (info lines, logo, image)
```

## Modules

| Module      | Role                                                                                       |
| ----------- | ------------------------------------------------------------------------------------------ |
| `cli`       | The clap definition of the command line.                                                   |
| `options`   | Turns `Cli` into `data::InfoOptions` (what to collect) and `render::RenderOptions` (how to print it). The only module that reads `Cli`, apart from `main`. |
| `data`      | Collects data. `build_info` returns an `Info`: a title and a list of `Field`s. `data::git` holds the repository queries shared by the fields, notably the single commit-graph traversal. |
| `language`  | The `Language` enum, generated by `build.rs` from `languages.yaml` and `src/language/language.tera`. |
| `render`    | Prints an `Info`: terminal layout, colors, ascii art, images, and JSON/YAML output.        |

Dependencies only go one way:

- `data` must not depend on `cli`, `options`, `render`, or colors.
- `render` must not depend on `cli` or `options`. (`cli` uses a few `render`
  types as flag values, such as `SerializationFormat` and `ImageProtocol`.)
- `language` is shared by `data` and `render`: its enum carries both data
  (tokei mapping, language type) and display information (logo, colors, chip).

Everything is one crate, so the compiler doesn't enforce these rules; keep
them in mind when reviewing imports in these modules.

## Options

The parsed command line (`Cli`) is only read by `options.rs` (and by `main` for
`--languages`, `--package-managers` and `--generate`). It is split into two
structs, one per stage:

| Struct          | Defined in      | Read by                    | Holds                                                                 |
| --------------- | --------------- | -------------------------- | --------------------------------------------------------------------- |
| `InfoOptions`   | `data/mod.rs`   | `data::build_info`         | What to collect: input path, disabled fields, how many authors, languages and file churns to keep, excluded globs, bot/merge filters, URL format, language types. |
| `RenderOptions` | `render/mod.rs` | everything in `render`     | How to print it: JSON/YAML or terminal, ascii art or image (and its protocol and color resolution), logo and text colors, bold, and how values look in the info lines (number separator, ISO dates, true colors and Nerd Font icons for language chips, color palette row). |

When adding a flag: if it changes what is collected, and therefore the
JSON/YAML output, it belongs in `InfoOptions` (like `--number-of-authors`);
if it only changes how things are printed, in `RenderOptions` (like
`--iso-time` or `--no-art`).

## Collecting data (`data`)

`build_info` opens the repository and computes the expensive inputs once, in
parallel: lines of code per language (tokei, in a thread) and commit statistics
(one commit-graph traversal). `InfoBuilder` (`data/builder.rs`) then adds each
enabled field, in the order `build_info` calls it.

Each field is a plain data struct in `data/fields/<name>.rs` with a constructor.
`data/fields/mod.rs` defines `FieldKind` (what `--disabled-fields` takes) and
`enum Field`, one variant per field holding its data. The `Serialize` impl of
`Field` is the JSON/YAML format of `-o` (`{"HeadInfo": {...}}`), so treat it as a
public format.

## Displaying data (`render`)

`render/fields/<name>.rs` implements `FieldView` (`key` and `value` lines) for
the field of the same name in `data/fields/`, using `RenderOptions` (and the
number and date helpers in `render/format.rs`). `render::lines` turns an
`Info` into the title, the "Key: value" lines and the color palette row, as
styled text (`render::style`), which `render::style::render` writes with
terminal escape codes. `render::Printer` (`render/printer.rs`) places those lines next to the logo,
either ascii art (`render::logo`) or an image (`render::image`), or prints
JSON/YAML instead.
