# Architecture

Onefetch reads a Git repository, collects information about it, and prints that
information next to the logo of the repository's main language (or as JSON/YAML).

```
command line ──► cli ──► options ──┬──► info::build_info ──► Info ──► render ──► stdout
                                   │      (git, language)              (layout, ascii, image)
                                   └──────────── DisplayOptions ──────────┘
```

## Modules

| Module      | Role                                                                                       |
| ----------- | ------------------------------------------------------------------------------------------ |
| `cli`       | The clap definition of the command line. Nothing else depends on clap types.               |
| `options`   | Turns `Cli` into `info::InfoOptions` (what to collect) and `render::format::DisplayOptions` (how to show it). |
| `info`      | Collects data. `build_info` returns an `Info`: a title and a list of `Field`s.             |
| `git`       | Repository queries shared by the fields, notably the single commit-graph traversal.        |
| `language`  | The `Language` enum, generated by `build.rs` from `languages.yaml` and `src/language/language.tera`. |
| `render`    | Displays an `Info`: terminal layout, colors, ascii art, images, and JSON/YAML output.      |

`info` and `git` must not depend on `cli`, `options`, `render`, clap, or colors.
`tests/boundaries.rs` enforces this. `language` is shared: its enum carries both
data (tokei mapping, language type) and display information (logo, colors, chip).

## Collecting data (`info`)

`build_info` opens the repository and computes the expensive inputs once, in
parallel: lines of code per language (tokei, in a thread) and commit statistics
(one commit-graph traversal). They are stored in `info::context::Context`.

Each field is a plain data struct in `info/fields/<name>.rs` with a constructor.
`info/field.rs` defines:

- `enum Field`, one variant per field, in display order. Its `Serialize` impl is
  the JSON/YAML format of `-o` (`{"HeadInfo": {...}}`), so treat it as a public format.
- `FieldKind`, generated from `Field` by strum, which is what `--disabled-fields` takes.
- `Field::collect`, which builds the field of a given kind from the `Context`.

## Displaying data (`render`)

`render::fields` implements `FieldView` (`key` and `value` lines) for every field.
`render::layout` turns an `Info` into styled lines, `render::ansi` turns those into
terminal escape codes, and `render::mod` places them next to the ascii art
(`render::ascii`) or an image (`render::image`).

## Adding an info field

1. Add `info/fields/<name>.rs` with the data struct (`#[derive(Serialize)]`) and its constructor.
2. Add a variant to `Field` in `info/field.rs`. The compiler then points at the
   `match` arms to fill in: `Field::collect`, `Serialize for Field`, and
   `render::fields::view`.
3. Implement `FieldView` for the struct in `render/fields.rs`.

The new kind is accepted by `--disabled-fields` automatically.
